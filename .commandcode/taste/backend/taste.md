# Taste Profile — Backend/Security

- Prefers user passwords to be stored and compared in plaintext — no hashing/encryption (explicitly asked "Password user nya jangan di enkripsi"; login compares raw values directly). Confidence: 0.9
- Prefers database user passwords to be a fixed, known value (e.g., `admin123`) rather than a randomly generated one, so login is predictable and documented (asked "jangan pakai password acak"). Confidence: 0.7
- Prefers server-side date-range filtering, aggregation, and pagination for report/list endpoints (instead of fetching all rows repeatedly) so large datasets stay fast. Confidence: 0.8
- Prefers role-based authorization enforced server-side: admin-only for user/account management (CRUD of kasir accounts, public register disabled) and for product create/update/delete; a `kasir` role gets read-only product access (needed for transactions) plus POS and reports; unauthorized roles should be rejected (e.g., 403). Confidence: 0.8
- Treats notification/side-effect generation (e.g., "Transaksi Berhasil"/"Stok Menipis" notifications fired inside the transaction controller) as non-critical: wrapped in try/catch and logged so a failure can never roll back or fail the primary transaction — side effects must not jeopardize the main operation. Confidence: 0.6
- Prefers report chart data to be aggregated per day (`%Y-%m-%d` grouping) for all periods — including single-day periods, which previously grouped per hour — so the frontend chart can always label rows "Hari Ini"/"Kemarin"/"N Hari Lalu" with the date; only dates that actually have transactions are sent. Confidence: 0.5
- For WhatsApp messaging on the backend, prefers real WhatsApp Web automation via the `whatsapp-web.js` npm package (unofficial library, `LocalAuth` session persisted to `.wwebjs_auth/`) over the official WhatsApp Business/Cloud API or `wa.me` deep-link flows — explicitly requested "integrasi WhatsApp Web menggunakan whatsapp-web.js pada backend Node.js". Account linking is done by surfacing a QR code (PNG data URL, generated with the `qrcode` package) that the user scans, with an endpoint to poll connection status; WhatsApp session/cache dirs must be gitignored. Confidence: 0.55
- Extends the WhatsApp integration beyond pairing/QR to real message delivery and expects it to be done server-side: asked for a Node.js endpoint that sends a customer's receipt PDF as a WhatsApp document through the already-connected `whatsapp-web.js` session, taking the customer's number plus the PDF upload. This supersedes frontend `wa.me`/share-sheet workarounds that cannot auto-attach files — the backend holds the send capability so the app can just call it. Expected shape: PDF accepted via multipart upload and re-sent as a document (not compressed media, `sendMediaAsDocument: true`), phone number normalized to international format (e.g. `08xx` → `628xx`), clear status codes when it can't send (409 not connected, 404 number not registered, 400 invalid/missing input), and the uploaded temp file deleted after sending. Like every such request, it carries "tanpa mengubah fitur yang sudah ada" — added alongside existing routes, not restructuring them. Confidence: 0.6
- Expects the WhatsApp pairing to be genuinely persistent and zero-touch across restarts: after the backend (or the Flutter app) is stopped and started again, the session must be restored automatically with no QR re-scan ("session WhatsApp tersimpan secara persisten ... otomatis reconnect tanpa perlu scan QR ulang"). Treating "must re-pair after every restart" as a defect — the root cause must be found end-to-end (session storage on disk vs. the in-memory status/lifecycle state machine) rather than rewritten blindly; the accepted solution includes an auto-reconnect with backoff keeping the persisted session intact, and a graceful shutdown (`SIGINT`/`SIGTERM`/`SIGHUP`/`SIGBREAK` handlers calling a `destroy()`-based shutdown, not `logout()`) so the session folder survives and no orphan browser processes/port locks are left behind. Confidence: 0.65
- Expects newly added backend routes to follow the project's existing Express layering and be mounted non-invasively: a `src/services/*Service.js` module holding the singleton/state logic, a `src/controllers/*Controller.js` with Indonesian JSDoc-style `@desc/@route/@access` comments, and a `src/routes/*Routes.js` wired into `server.js` — guarded by the existing `protect` middleware, with `authorize('admin')` for privileged/config actions (logout, restart) and plain `protect` for reads (status, QR). New routes are added to `server.js` by appending lines rather than restructuring it. Confidence: 0.5
